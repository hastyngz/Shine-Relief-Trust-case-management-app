# Firestore read-cost findings: live listener architecture

Review date: 2026-10-14  
Branch: `Replit`

## Most important finding

The app's central synchronization service, `src/services/firestoreSync.ts`, creates a large set of Firestore `onSnapshot` listeners in `initFirestoreListeners()`. It builds a full in-memory `AppDatabase` from those listeners and notifies the app when snapshots arrive.

The listeners cover girls, households, education/health/family follow-ups, rent payments, expenses, activities, contacts, budgets, annual budgets, payroll, employees, workplans, schedules, meetings, feeding-program logs, market prices, forecast settings, what-if scenarios, intelligence suggestions, AI settings, historical records, import audits, restricted import source data, early-years records, people, case actions, education history, academic supports, examinations, attendance, girl leave, programme logs, case reviews, case goals, procurement lists, and project projections.

Most of these are collection-wide listeners. There are a few deliberate exceptions:
- `caseActions` is queried by assigned staff UID when the user cannot view team tasks.
- `historicalRecords` is filtered to permitted record types when the user cannot view health records.
- Some restricted collections are skipped entirely when the caller's supplied permission flags disallow access.

The service waits for its expected collection count before marking the initial sync complete. That means the app's current data model is intentionally based on live snapshots, not a collection of independent one-time fetches.

## Why this matters for Cloudflare KV

A Worker/KV GET endpoint cannot save the reads generated by these subscriptions unless the app stops using the relevant Firestore listeners and the full read/write/update behavior is redesigned. Adding a cached endpoint while leaving the listener active would create duplicate paths, not savings.

Cloudflare KV is also eventually consistent. Replacing live subscriptions with periodic cached responses could make changes made by one staff member appear late to another. That is especially risky for operational records and inappropriate for sensitive case, health, safeguarding, payroll, expense, and audit information.

## Recommended order of work

1. **Measure before changing behavior.** Record Firestore usage by collection and compare a representative active session, including initial load and normal editing. Do not infer savings from a cache hit counter alone.
2. **Reduce unnecessary reads at their source.** Review whether every role and every screen genuinely needs every collection subscribed at application startup. Consider role-aware and screen/on-demand subscriptions while preserving current permissions and required live updates. This may reduce reads without introducing a second data transport.
3. **Keep sensitive/live data source-authoritative.** Do not route case records, health or family follow-ups, safeguarding, staff identity, contacts, payroll, expenses, payments, messages, or audit information through KV in the first rollout.
4. **Choose a real cache pilot only after call-site tracing.** It must be a repeated, one-shot, low-sensitivity read with a clear freshness requirement and a complete inventory of all writers. Route that actual caller through the Worker, verify Firebase identity and current staff status for every request, and ensure every mutation invalidates or versions the cache.
5. **Test and measure.** Cover authorization, permission changes, stale entries, deletion, cache misses, KV failure, and multi-user behavior. Compare Firestore read metrics against the baseline before claiming savings.

## Guardrails

- Keep Firebase/Firestore as the source of truth.
- Do not cache authentication tokens or role/permission decisions as authoritative data.
- Do not use shared cache keys for private/user-scoped results.
- Do not enable broad persistent client caching as a shortcut; this app handles sensitive data and may be used on shared staff devices.
- Preserve live update behavior unless a deliberate, tested product decision changes it.
- Keep all changes on `Replit`; do not change `main`.
- No production deployment or cost reduction is claimed by this audit.

## Current status

The KV binding exists, but no application data read is routed through KV. The strongest finding so far is that the app's central live-sync design—not a missing KV binding—is the main obstacle to reducing reads through edge caching. The next safe engineering change should first establish a measured baseline and review which listeners are necessary for each role and screen, rather than inserting a disconnected cache.
